# Add Test Skill

Напиши тест(и) для файлу, переданого як аргумент, дотримуючись тестових
конвенцій цього монорепо.

## Аргументи

- $0 — шлях до файлу, для якого потрібен тест (обов'язковий, відносний до
  кореня репо або воркспейсу, напр. `apps/backend/src/categories/category.mapper.ts`)
- $1 — опис того, що саме перевірити (опційно; якщо не вказано — покрий
  публічну поведінку файлу: happy path + основні edge cases)

Якщо $0 не передано — запитай користувача шлях, не вгадуй.

## Алгоритм виконання

1. Прочитай файл $0 повністю, щоб зрозуміти його публічний інтерфейс
   (експортовані функції/класи/ендпоінти) та залежності.

2. Визнач, до якого воркспейсу належить файл, і яка тестова конвенція діє:

   - **`apps/backend`** — Jest, e2e-тести в `apps/backend/test/*.e2e-spec.ts`.
     - Контролери/модулі з ендпоінтами → e2e-тест за зразком уже наявних
       (`apps/backend/test/categories.e2e-spec.ts`,
       `apps/backend/test/transactions.e2e-spec.ts`, `auth.e2e-spec.ts`):
       піднімають застосунок через `createTestApp()` з
       `apps/backend/test/utils/test-app.ts`, чистять таблиці через
       `prisma.$executeRawUnsafe('TRUNCATE TABLE "..." CASCADE')` в
       `beforeAll`, ходять через `supertest`, авторизуються через
       `/auth/register`, перевіряють ownership на другому користувачі
       (`otherToken`).
     - Чисті функції без Nest-контексту (mapper, handler, hasher-логіка) —
       постав тест поруч у `*.spec.ts`, якщо в модулі вже є такий приклад;
       інакше додай його в `apps/backend/test/` за аналогією з існуючими
       e2e-файлами, але без підйому HTTP-рівня, якщо це не потрібно.
     - DTO та ендпоінти — типи з `@repo/shared`, ніколи не редеклеровані
       локально.
     - Команда запуску: `npm run test:e2e --workspace=apps/backend`
       (потрібен запущений PostgreSQL — `docker compose up -d`).

   - **`apps/frontend`** — у репозиторії ще немає тестового раннера
     (`package.json` не має `test`-скрипта). Перед написанням тесту:
     1. Перевір ще раз `apps/frontend/package.json` і чи не з'явився
        раннер відтоді.
     2. Якщо раннера немає — повідом користувача, що для фронтенду
        потрібно спершу підключити тестовий інструмент (напр. Vitest +
        Testing Library), і запитай, чи додати мінімальну конфігурацію,
        перш ніж писати сам тест. Не вигадуй конвенцію мовчки.

   - **`packages/shared`** — чисті типи/DTO без логіки зазвичай тестів не
     потребують; якщо у файлі є функція з логікою (не лише інтерфейси), онови
     backend-конвенцію (найближчий `*.spec.ts` поруч із файлом) і запусти її
     через `npm run test:e2e --workspace=apps/backend`, якщо тест живе там,
     або постав поруч у `packages/shared` з окремим `*.spec.ts`, якщо там уже
     є Jest-конфіг для пакету.

3. Напиши тест(и):
   - Покрий happy path + мінімум один edge case (валідація, 404/403,
     ownership, порожній ввід — залежно від файлу).
   - Якщо $1 передано — реалізуй саме той сценарій, а не вигадуй додаткові
     без потреби.
   - Дотримуйся стилю сусідніх тестових файлів (іменування `describe`/`it`,
     хелпери, порядок `beforeAll`/`afterAll`).

4. Запусти тести, щоб переконатись, що вони проходять:

```bash
npm run test:e2e --workspace=apps/backend
```

   Якщо тест не для backend і раннера немає — пропусти цей крок і повідом
   про це користувачу.

5. Покажи короткий підсумок: який файл покрито, де лежить новий тест-файл,
   і результат запуску.

## Правила

- Не редагуй файл, для якого пишеться тест, якщо це прямо не потрібно для
  тестованості (напр. новий `export`) — і в такому разі повідом користувача
  окремо.
- Не вигадуй тестовий фреймворк для воркспейсу, де його ще немає — спитай.
- Новий тест-файл follow existing naming: `*.e2e-spec.ts` для e2e,
  `*.spec.ts` для юніт-тестів поруч із файлом.
- Не комить і не пуш — це окремі кроки (див. скіли `commit-to-branch`, `pr`).
