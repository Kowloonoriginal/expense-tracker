# План: стан сесії, header з виходом і UX-доробки авторизації

Створено: 2026-09-03
Статус: виконано 2026-09-03

---

## Контекст

Сторінки логіну й реєстрації готові (див. `2026-09-02-login-register.md`), але
свідомо лишились без стану сесії: форми зберігають токен у `localStorage` і
роблять редірект на `/`, після чого застосунок про користувача «не знає».
Чотири пункти, відкладені тим раундом, тепер реалізуються:

1. `AuthContext` (стан сесії) + header з іменем користувача та кнопкою «Вийти».
2. Редірект уже залогінених із `/login` і `/register`.
3. Показ/приховання пароля.
4. Локалізація повідомлень бекенду (409/401/429 лишались англійською).

Наслідок для архітектури: header композує дані `entities/session` з дією
(вихід) — це класичний **widget** у FSD, тож у `apps/frontend/src` з'являється
шар `widgets`, якого досі не було. `CLAUDE.md` оновлюється відповідно (там
зараз написано, що `widgets` пропущено).

---

## Етап 1. Стан сесії — `entities/session/model/session-context.tsx`

`SessionProvider` + хук `useSession()`:

```ts
interface SessionContextValue {
  user: User | null;
  isLoading: boolean; // true, поки не прочитано localStorage
  startSession: (auth: AuthResponse) => void; // saveSession + setUser
  endSession: () => void; // clearSession + setUser(null)
}
```

`localStorage` читається **в `useEffect`**, а не при ініціалізації стану:
серверний рендер і перший клієнтський мусять збігатись, інакше React кине
помилку гідратації. Звідси `isLoading` — споживачі не малюють нічого
залежного від сесії, поки він `true`.

Провайдер вмикається в `app/layout.tsx` (сам layout лишається серверним
компонентом, `SessionProvider` — клієнтський дочірній).

## Етап 2. Редірект залогінених — `entities/session/model/use-redirect-if-authenticated.ts`

Малий хук: коли `!isLoading && user` — `router.replace('/')`. Повертає
`isChecking`, щоб форма не блимала перед редіректом. Живе в `entities/session`,
бо читає стан сесії; `shared` для нього не підходить (нижчий шар не може
залежати від entities).

## Етап 3. Локалізація помилок — `entities/session/model/auth-error.ts`

```ts
authErrorMessage(error: unknown): string;
```

Мапить статуси, які реально показуються в auth-формах:

| Статус      | Повідомлення                                |
| ----------- | ------------------------------------------- |
| 401         | Невірний email або пароль                   |
| 409         | Користувач з таким email вже існує          |
| 429         | Забагато спроб. Спробуйте за хвилину.       |
| інші        | текст із `ApiError` (400 несе деталі полів) |
| не ApiError | Щось пішло не так. Спробуйте ще раз.        |

Лежить в `entities/session`, а не в кожній фічі: обидві форми показують той
самий текст для тих самих кодів, і це інтерпретація відповіді auth-API, яким
володіє саме ця сутність.

## Етап 4. Показ/приховання пароля — `shared/ui/form-field.tsx`

Не окремий компонент, а проп `revealable` у наявному `FormField`: інакше
довелось би дублювати розмітку label+input+error. Всередині — локальний стан,
`type` перемикається `password`↔`text`, кнопка-іконка (`Eye`/`EyeOff` з
`lucide-react`, вже встановлений) з `type="button"` (щоб не сабмітила форму)
та `aria-label`, що змінюється.

## Етап 5. Widget header — `widgets/header/`

```
widgets/header/
  ui/Header.tsx   ім'я користувача + «Вийти», або лінк «Увійти» для гостя
  index.ts
```

Окремої слайси `features/logout` **не** створюю: уся логіка виходу — це
`endSession()` сутності сесії, окремої бізнес-логіки понад те немає, а слайс
заради одного виклику — надлишкове дроблення (антипатерн FSD не менший, ніж
відсутність шарів). Якщо вихід обросте логікою (підтвердження, інвалідація
токена на бекенді) — виділиться у `features/logout`.

Лінки-кнопки використовують `buttonVariants(...)` на `<Link>`, а не
полиморфний `render`-проп Base UI — менше зав'язки на API конкретної версії.

Layout стає flex-колонкою (`header` + `flex-1` контент), сторінки міняють
`min-h-screen` на `flex-1`, інакше з хедером з'явиться зайвий скрол.

## Етап 6. `CLAUDE.md`

Оновити діаграму шарів: додати `widgets` між `app` і `features`, прибрати
твердження, що цей шар пропущено (`pages` лишається пропущеним).

### Що показала перевірка в браузері

1. Сесія з попереднього прогону піднялась із `localStorage` — хедер одразу
   показав «Тестовий Юзер» + «Вийти», без помилок гідратації в консолі.
2. `/login` для залогіненого → `router.replace('/')`, форма не блимнула.
3. «Вийти» → `localStorage` порожній (`token: null`, `user: null`), редірект
   на `/login`, хедер перемкнувся на гостьовий лінк «Увійти».
4. Кнопка-око показує/ховає пароль, `aria-label` міняється
   («Показати пароль» ↔ «Сховати пароль»), форму не сабмітить.
5. Невірний пароль → **«Невірний email або пароль»** (було англійське
   `Invalid email or password`).
6. Повторна реєстрація існуючого email → **«Користувач з таким email вже
   існує»** (було `User with this email already exists`).
7. Успішний логін → редірект на `/`, хедер знову з іменем користувача.

## Не входить у цей раунд

- Поле «підтвердіть пароль» на реєстрації (користувач відхиляв раніше; окремо
  від показу/приховання пароля).
- Серверний захист роутів (`middleware.ts`) — неможливий без cookie, а токен
  свідомо в `localStorage`.
- Автоматичне продовження/оновлення токена, реакція на 401 у фонових запитах.
