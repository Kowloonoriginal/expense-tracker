# План: головний екран + пагінація на бекенді

Створено: 2026-09-08
Статус: виконано 2026-09-08

---

## Контекст

Завдання: головний екран трекера — меню (транзакції / категорії), профіль
користувача, список транзакцій із пагінацією по 10, плюс те, що я вважатиму за
потрібне.

**Ухвалено з користувачем до планування:**

1. **Пагінація — на бекенді.** `GET /transactions` приймає `page`/`limit` і
   віддає `{ items, total, page, limit }`. Користувач прийняв, що це змінює
   форму відповіді й ламає наявні e2e-ассерти.
2. **Обсяг — перегляд + створення.** Екран, навігація, профіль, пагінований
   список, сторінка категорій і форми _створення_ транзакції та категорії.
   Редагування й видалення — наступний раунд.

**Три блокери, знайдені під час розвідки — жоден не опційний:**

- `apiFetch` у `shared/api/client.ts` **не надсилає `Authorization`**. Будь-який
  запит до `/transactions` чи `/categories` сьогодні поверне 401. Токен живе в
  `entities/session`, а `shared` не має права імпортувати `entities` — тож це
  вимагає рішення про шари, а не однорядкової правки.
- `Transaction.date` / `createdAt` типізовані як `Date` у `@repo/shared`, але
  приходять **ISO-рядками** (`apiFetch` робить голий `response.json()`). Тобто
  `transaction.date.toLocaleDateString()` проходить перевірку типів і падає в
  рантаймі.
- **Немає гарда для авторизованих сторінок** — є лише зворотний хук для
  `/login`. Анонім побачив би каркас дашборда до того, як спрацює редірект.

Перевірено: `TransactionsRepository.findAllForUser` має рівно одного викликача
(`get-transactions.handler.ts:33`); однойменний метод у репозиторії категорій —
інший клас, його не чіпаємо. Рівно **11 ассертів** у `transactions.e2e-spec.ts`
ламаються на конверті (рядки 159, 219, 220, 340, 342, 344, 348, 351, 352, 353, 354) — усі механічно `body` → `body.items`.

## Етап 1. Пагінація на бекенді

`@repo/shared` отримує перевикористовуваний конверт. `totalPages` свідомо
відсутній — це `Math.ceil(total / limit)`, а друге джерело правди для одного
числа рано чи пізно розійдеться з першим.

```ts
export interface Paginated<T> {
  items: T[];
  total: number;
  page: number;
  limit: number;
}
export interface PaginationQueryDto {
  page?: number;
  limit?: number;
}
export interface TransactionListQueryDto
  extends TransactionFiltersDto, PaginationQueryDto {}
```

`TransactionFiltersDto` лишається як є — фільтри обирають, _які_ рядки,
пагінація ріже результат; злиття зробило б контракт фільтрів брехливим.

**DTO:** `page` за замовчуванням 1 (`@Min(1)`), `limit` — 10, максимум 100.
Обидва потребують `@Type(() => Number)`: глобальний `ValidationPipe` працює без
`enableImplicitConversion`, прецедент — `transaction-summary.query.dto.ts`.

**Репозиторій:** замість `findAllForUser` — `findPageForUser(userId, filters,
{ skip, take })`. `where` будується **один раз** і використовується і в
`findMany`, і в `count`, обидва в одному `prisma.$transaction` — інакше вставка
між двома окремими запитами дасть count, який описує інший набір рядків, ніж
сторінка. Наявний `@@index([userId, date])` це вже обслуговує; міграція не
потрібна.

**Сторінка за межею:** 200 з `items: []`, справжнім `total` і `page`, відлунним
як запитали — не обрізаємо й не 404. Номер сторінки, що застарів після
видалення, — це буденність, і клієнт сам бачить, що перелетів.

## Етап 2. Шов авторизації (шари FSD)

**Обрано: порт-провайдер токена в `shared/api`, адаптер вкручує
`entities/session`.**

```ts
export function setAuthTokenProvider(provider: () => string | null): void;
export function setUnauthorizedHandler(handler: (() => void) | null): void;
```

`apiFetch` додає `Authorization` лише за наявності токена (анонімний
`/auth/login` не має слати `Bearer null`).

Відхилено: передавати токен у кожен виклик (перетворює інфраструктуру на
параметр кожної api-функції й кожного замикання у віджеті) і опустити зберігання
токена в `shared` (спокусливо — жодного вкручування — але _життєвий цикл_ токена
це поведінка сесії; розділивши зберігання й цикл, дістанемо два власники одного
ключа).

**401 в одному місці.** В `apiFetch`: `if (status === 401 && token)
onUnauthorized?.()` — і далі однаково кидає. **Наявність токена і є
дискримінатором**: 401 _з_ токеном означає, що токен протух → вихід; 401 _без_
токена — це невдалий вхід, і він не має нічого чистити, інакше друкарська
помилка в паролі викидала б сторінку логіну саму з себе.

Порядок реєстрації важливий: **провайдер токена реєструється на рівні модуля** в
`session-storage.ts`, не в ефекті — ефекти дітей виконуються раніше за ефекти
батьків, тож перший запит віджета випередив би `useEffect` провайдера.
**Обробник 401** реєструється в ефекті `SessionProvider` (він лише
_викликається_ пізніше).

## Етап 3. Дати — `@repo/shared` переходить на ISO-рядки

`@repo/shared` описує HTTP-контракт, а в JSON немає `Date`. Nest уже серіалізує
ці поля як ISO-рядки, тобто тип завжди був неправдивим.

`User.createdAt`, `Transaction.date`, `Transaction.createdAt` → `string`. Два
маппери викликають `.toISOString()` явно — **тіла відповідей байт-у-байт ті
самі**, бо `JSON.stringify(date)` _і є_ `toISOString()`. Усе внутрішнє лишається
справжніми `Date`: межі `gte`/`lt` у репозиторії, `Date.UTC` у вікні місяця,
`new Date(command.date)` у хендлерах.

Форматування — у `shared/lib/format.ts` (`formatDate`, `formatAmount` через
`user.currency`, `formatSignedAmount`).

## Етап 4. Гард роутів

`useRequireAuth` + `<RequireAuth>` в `entities/session` — точне дзеркало наявного
`useRedirectIfAuthenticated`. `isChecking` лишається `true`, поки сесія невідома
_і_ поки триває редірект; `children` при цьому **не змонтовані**, тож каркас не
малюється, а ефекти віджетів не встигають зробити запит без токена.
Застосовується один раз у `app/(app)/layout.tsx`.

`RequireAuth` фоново викликає `refreshUser()` (новий `me()`) — відкликаний токен
відсіється тут, а не на першому кліку.

**Чесне обмеження:** токен у `localStorage`, тож ні middleware, ні серверний
компонент його не бачать. Це UX-гард, а не межа безпеки — межа безпеки це
глобальний `JwtAuthGuard` на бекенді.

## Етап 5. Завантаження даних — один хук `useAsync` у `shared/lib`

Не заради боротьби з дублюванням (три копії `useState`/`useEffect` були б
терпимі), а заради **захисту від застарілої відповіді**: швидко клацнувши
1→2→3, можна отримати повільну відповідь сторінки 2 після третьої — і таблиця
покаже другу, поки пагінатор каже «3». Перевірка id запиту робить останній запит
авторитетним. Написати це правильно тричі вручну, в репозиторії без тестів, —
надійний спосіб отримати баг, який ніхто не відтворить.

Попередні дані зберігаються під час завантаження, тож перегортання приглушує
таблицю, а не згортає її у скелет.

## Етап 6. Нові слайси

```
entities/transaction/   api, model/transaction-query.ts (будівник URLSearchParams, що
                        викидає порожні значення — порожній select не має слати `type=`,
                        на якому @IsEnum дасть 400), ui/TransactionRow, ui/TransactionAmount
entities/category/      api, model/category-map.ts, ui/CategoryBadge (колір із Category.color —
                        --chart-1..5 це сірі градації)
features/create-transaction/  zod-схема, дзеркальна до правил бекенду, + TransactionForm
features/create-category/     схема + CategoryForm
widgets/transactions-panel/   список + фільтри + пагінатор + порожні стани
widgets/categories-panel/     сітка + створення
widgets/month-summary/        три плитки + топ-5 категорій
widgets/user-profile-card/    прямо з useSession, без запиту
widgets/header/ui/MainNav.tsx навігація в наявному слайсі хедера
shared/lib/{use-async,format}.ts, shared/ui/select-field.tsx
```

**Список — віджет, а не фіча.** Він мусить оновитись після успішного створення, а
це сусідні слайси; якби список був фічею, ключ оновлення довелося б тримати у
файлі роуту, який за конвенцією лишається тонким. Віджет може імпортувати фічі,
тож один віджет володіє обома й тримає ключ у себе.

**Фільтри лишаються всередині віджета** — правило самого `CLAUDE.md` («не
виділяй слайс заради одного тривіального виклику»): чотири контроли без сабміту,
що змінюють стан, яким віджет і так володіє.

**Навігація розширює `widgets/header`**, а не стає окремим віджетом. **Віджета
`dashboard` не буде**: віджет, що композить віджети, — це імпорт убік; сторінка,
що розкладає чотири віджети по сітці, лишається тонкою.

## Етап 7. Роути

```
app/page.tsx                     публічний лендинг — без змін
app/(app)/layout.tsx             'use client'; <RequireAuth> + контейнер
app/(app)/dashboard/page.tsx     MonthSummary + UserProfileCard + TransactionsPanel
app/(app)/transactions/page.tsx  TransactionsPanel з фільтрами й створенням
app/(app)/categories/page.tsx    CategoriesPanel
```

**Дашборд на `/dashboard`, не на `/`.** `/` — публічна статична сторінка, на яку
посилаються `/privacy`, `/terms` і хедер; зробивши її дашбордом, ми змусили б її
рендеритись на клієнті й повернули б блимання сесії саме на ту сторінку, куди
потрапляють аноніми.

## Етап 8. Що ще додаю

- **Підсумок місяця** — `/transactions/summary` написаний, покритий тестами й не
  використовується. Один запит дає доходи/витрати/баланс плюс розбивку по
  категоріях із власними кольорами.
- **Пастка першого запуску, і вона несуча:** `POST /transactions` вимагає

  може зробити, це отримати помилку. Форма бачить порожній список, блокує сабміт
  і веде на `/categories`.
- **Фільтри** поверх уже протестованих `dateFrom/dateTo/type/categoryId`, і
  **скелетони**. Валюта з `user.currency`, а не захардкоджена ₴.

**Не цього раунду:** редагування/видалення, бібліотека графіків, синхронізація
пагінації з URL, засівання дефолтних категорій, темна тема, пошук.

**shadcn:** `npx shadcn@latest add table skeleton badge avatar`. Свідомо **без**
`select` (у Base UI це не нативний контрол, потрібен `Controller` і неперевірений

`form-field.tsx`), без `dialog` і без `pagination`.

### Що показала перевірка

**Бекенд.** e2e 42/42 (6 нових на пагінацію). Межові випадки через curl:
`?page=3` → 3 елементи з 23; `?page=99` → 200 із порожнім `items`, `total=23`,
`page=99` (не 404); `?limit=101`, `?limit=0`, `?page=0`, `?page=abc` → 400;
`?type=INCOME&limit=2` → `total=4`, тобто count і сторінка справді бачать один
`where`. Поле `date` віддається як `2026-09-24T12:00:00.000Z` — байт-у-байт як
до зміни типів.

**Фронтенд** (Browser pane, 23 засіяні транзакції):

1. Анонім на `/dashboard` → редірект на `/login`, і **жодного запиту** до
   `localhost:3001` — діти справді не змонтовані, а не приховані.
2. Реєстрація → одразу `/dashboard`: навігація з трьох пунктів, картка
   профілю з датою `08.09.2026` (те, що падало б до переходу на ISO), підсумки
   по нулях, порожній стан списку.
3. Форма транзакції без категорій показала «Спочатку створіть категорію» з
   робочим посиланням — пастка першого запуску закрита.
4. Створення категорії — з'явилась одразу, без перезавантаження.
5. Список: 10 рядків, «Сторінка 1 з 3 · усього 23», «Назад» заблоковано, дати,
   кольорові бейджі, знакові суми (`−230,50 грн` / зелені `+200,50 грн`).
6. Два швидкі «Далі» поспіль → сторінка 3 з 3 рядками, лейбл і вміст збігаються
   — захист від застарілої відповіді тримає.
7. Фільтр `Дохід` → 4 рядки, сторінка скинулась на 1. У мережі:
   `?type=INCOME&page=1&limit=10`, а після «Скинути» — `?page=1&limit=10`
   **без** порожнього `type=`.
8. Підміна токена на `garbage` + перезавантаження → редірект на `/login`, обидва
   ключі `localStorage` очищено. Невірний пароль на `/login` показав помилку і
   **лишився** на сторінці — дискримінатор за наявністю токена працює.
9. Консоль: лише очікувані 401 з тестів вище, жодних попереджень гідратації.
