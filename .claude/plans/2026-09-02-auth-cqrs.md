## Етап 3. Модуль авторизації ✅

```
src/auth/
  auth.service.ts              bcrypt (10 раундів) + підпис JWT
  auth.controller.ts           POST /auth/register, POST /auth/login, GET /auth/me
  dto/register.dto.ts          class-validator: email, name ≥2, password 8–72
  dto/login.dto.ts
  strategies/jwt.strategy.ts   валідація токена → дістає user з БД
  guards/jwt-auth.guard.ts     APP_GUARD (глобальний), поважає @Public()
  decorators/                  @Public(), @CurrentUser()
  types/jwt-payload.type.ts    { sub, email }
```

| Метод | Ендпоінт         | Доступ     |
| ----- | ---------------- | ---------- |
| POST  | `/auth/register` | публічний  |
| POST  | `/auth/login`    | публічний  |
| GET   | `/auth/me`       | Bearer JWT |

Потік запиту (поточний, до CQRS):

```
POST /auth/login
  → ValidationPipe (whitelist)
  → JwtAuthGuard → бачить @Public() → пропускає
  → AuthController.login
  → AuthService.login → validateCredentials → UsersService → UsersRepository → Prisma
  → bcrypt.compare
  → JwtService.signAsync({ sub, email })
  → { accessToken, user }   ← user без passwordHash

GET /auth/me
  → JwtAuthGuard → passport-jwt: підпис + expiry
  → JwtStrategy.validate({ sub }) → БД → req.user
  → @CurrentUser() → toPublic()
```

**Рішення, прийняті на цьому етапі:**

- Guard зареєстровано глобально через `APP_GUARD`, а не поштучно на роутах →
  кожен майбутній контролер захищений із моменту створення (secure by default).
- `JwtStrategy.validate()` ходить у БД замість довіри payload-у → видалений
  акаунт втрачає доступ одразу, а не через 7 днів.
- DTO — класи з `!:`, бо `class-validator` працює з рантайм-метаданими, а
  `strict: true` вимагає ініціалізатор.

## Навіщо CQRS далі

`AuthModule` імпортує `UsersModule` і смикає `UsersService` напряму. Це працює,
але коли додадуться `categories` та `expenses`, граф імпортів стане в'язким:
реєстрація має створити дефолтні категорії → `UsersModule` імпортує
`CategoriesModule`, а той для скоупу даних потягнеться назад до користувача →
циклічна залежність і `forwardRef()`.

CQRS розриває цей граф: модулі спілкуються через шину, знаючи лише **контракти**
(класи команд/запитів), а не реалізації.

Що варто пам'ятати:

- У Nest CQRS шина — **не** черга і не мережа. `CommandBus.execute()` синхронний
  і кидає ті самі HTTP-винятки (`ConflictException` долетить до контролера).
  Купується розв'язка залежностей, а не асинхронність.
- Розділення Command/Query — не про два сховища, а про правило: команда змінює
  стан і не повертає дані для читання, запит повертає дані й нічого не змінює.
- `EventBus` — єдине місце зі справжньою асинхронністю, де реакції на подію не
  знають одна про одну. Головний виграш для «зареєструвався → створити дефолтні
  категорії → надіслати вітальний лист».

## Етап 5. Спільний модуль хешування ✅

Щоб `UsersModule` не залежав напряму від bcrypt, хешування ховається за токеном:

```
src/security/
  password-hasher.ts        interface PasswordHasher + PASSWORD_HASHER токен
  bcrypt-password-hasher.ts реалізація (10 раундів)
  security.module.ts        @Global(), exports: PASSWORD_HASHER
```

```ts
export interface PasswordHasher {
  hash(plain: string): Promise<string>;
  verify(plain: string, hash: string): Promise<boolean>;
}
```

Побічний виграш: у e2e-тестах провайдер підміняється фейком, і набір не платить
~80 мс bcrypt за кожну реєстрацію.

## Етап 6. Rate limiting замість вирівнювання часу ✅

```
ThrottlerModule.forRoot([{ ttl: 60_000, limit: 100 }])   // загальний
APP_GUARD: ThrottlerGuard                                 // глобально
@Throttle({ default: { ttl: 60_000, limit: 5 } })         // на /auth/login
@Throttle({ default: { ttl: 3_600_000, limit: 10 } })     // на /auth/register
```

Ключ тротлінгу для логіна — пара IP + email, а не лише IP: інакше один NAT
блокує весь офіс, а розподілений перебір одного акаунта проходить повз ліміт.

**Відхилення від плану:** окремий `LoginThrottlerGuard` не знадобився —
`@Throttle` у v6 приймає `getTracker` прямо в опціях роута. Це не лише
лаконічніше: другий guard через `@UseGuards` читав би ту саму метадату, що й
глобальний, і роут рахувався б двічі — глобальним трекером за IP (тобто знову
з проблемою NAT) і кастомним за IP+email.

Замість постійного `verify()` проти фіктивного хеша — **рандомізована затримка
(jitter) лише на негативних відповідях**. Сама по собі вона сигнал не прибирає,
а зашумлює (усереднення по кількасот запитів його відновлює), але під лімітом у
5 спроб/хв стільки вимірювань зробити неможливо. Зв'язка throttler + jitter
дешевша за постійний bcrypt і не створює вектора DoS.

## Етап 7. Контракти модуля користувача ✅

Назовні `UsersModule` віддає **тільки** папку `contracts/`. Репозиторій, сервіс і
хешер — внутрішні.

```
src/users/
  contracts/
    index.ts                        єдина публічна поверхня модуля
    commands/create-user.command.ts       ← містить plaintext, див. нижче
    queries/get-user-by-id.query.ts
    queries/verify-password.query.ts      ← (email, password) → userId | null
    events/user-registered.event.ts
    models/user.read-model.ts             без passwordHash
  handlers/
    create-user.handler.ts          @CommandHandler — хешує через PASSWORD_HASHER
    get-user-by-id.handler.ts       @QueryHandler
    verify-password.handler.ts      @QueryHandler — хеш не покидає модуль
  users.repository.ts               internal
  users.module.ts
```

**Рішення:** хеш пароля ніколи не перетинає межу модуля. `VerifyPasswordQuery`
приймає plaintext і повертає `userId | null` — `AuthModule` не знає ні формату
зберігання, ні алгоритму.

Симетричний наслідок: якщо `users` володіє перевіркою, він володіє й хешуванням.
Інакше bcrypt живе у двох модулях. Тому `CreateUserCommand` несе **plaintext**.

Ризик — не в самій шині (пароль уже прийшов у DTO), а в тому, що CQRS-логери й
інтерсептори серіалізують команди цілком:

```ts
export class CreateUserCommand {
  constructor(
    readonly email: string,
    readonly name: string,
    readonly password: string,
  ) {}

  toJSON() {
    return { email: this.email, name: this.name, password: '[REDACTED]' };
  }
}
```

`UsersService` розчиняється в хендлерах — перевірка дублікату і `toPublic`
переїжджають туди, де їм місце.

## Етап 8. Переведення auth на шину ✅

```
src/auth/
  commands/
    register-user.command.ts + handler
    login-user.command.ts + handler
  auth.controller.ts          → CommandBus.execute(...)
  strategies/jwt.strategy.ts  → QueryBus.execute(new GetUserByIdQuery(sub))
```

Після рефакторингу `AuthModule` не імпортує ні `UsersModule`, ні bcrypt — тільки
типи з `@/users/contracts`. Його зона відповідальності звужується до видачі й
перевірки токенів.

Реєстрація:

```
POST /auth/register
  → CommandBus: RegisterUserCommand
      RegisterUserHandler (auth)
        → CommandBus: CreateUserCommand(email, name, password)
            CreateUserHandler (users)
              → PASSWORD_HASHER.hash()
              → repository.create()
              → EventBus: UserRegisteredEvent
        → JwtService.sign()
  → AuthResponse
```

Логін:

```
POST /auth/login
  → ThrottlerGuard (5/хв на IP+email)
  → CommandBus: LoginUserCommand
      LoginUserHandler
        → QueryBus: VerifyPasswordQuery(email, password) → userId | null
        → null? jitter-затримка → 401 «Invalid email or password»
        → QueryBus: GetUserByIdQuery(userId) → UserReadModel
        → sign
```

Логін лишається **командою**, попри те що переважно читає: він видає токен, а
згодом сюди ляже `lastLoginAt`, лічильник невдалих спроб, аудит-лог. Запит за
визначенням не має права на ці побічні ефекти.

## Ухвалені рішення

**Захист від перебору — rate limiting, не вирівнювання часу.**
`@nestjs/throttler` з жорстким лімітом на `/auth/login` плюс jitter на негативних
відповідях. Постійний `bcrypt.compare` проти фіктивного хеша відкинуто: він
створює вектор DoS (80 мс CPU на кожен запит із випадковим email), а під
throttler-ом кількість вимірювань недостатня, щоб зняти шум із jitter.

**Межу модуля перетинає результат перевірки, не хеш.**
`VerifyPasswordQuery(email, password) → userId | null`. Перевірка автентичності —
частина доменної логіки користувача, і те, що `users` про неї знає, архітектуру
не порушує. Залежність від bcrypt ховається за токеном `PASSWORD_HASHER`.

## Відкрите питання

**`POST /auth/register` віддає 409 на зайнятий email — це прямий оракул
перелічення**, який не потребує жодних вимірювань часу. Більший за таймінговий
витік, який ми щойно закрили. Варіанти:

1. **Лишити 409.** Чесна UX-помилка «email вже зайнятий». Так робить більшість
   продуктів, бо приховати факт реєстрації все одно неможливо: форма
   відновлення пароля розкаже те саме.
2. **Завжди 202 Accepted** + лист на вказану адресу (або «підтвердіть пошту», або
   «хтось намагався зареєструватись на вашу адресу»). Оракул зникає повністю,
   але потрібен поштовий канал і підтвердження email.
3. **409 під тим самим throttler-ом** (10 спроб/год на IP). Компроміс: оракул
   лишається, але масове перелічення стає непрактичним.

**Ухвалено варіант 3:** 409 лишається, під лімітом 10 реєстрацій/год на IP.
Коли з'явиться підтвердження email, ендпоінт переходить на варіант 2 — замість
коду підтвердження надсилається лист «акаунт уже існує, увійдіть», і оракул
зникає без окремої роботи.
