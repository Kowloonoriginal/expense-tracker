# API

Детальний опис усіх ендпоінтів бекенду. Інтерактивна версія з можливістю
викликати запити прямо з браузера — Swagger UI на
`http://localhost:3001/api/docs` (лише коли `npm run dev:backend` запущено).

**Базовий URL:** `http://localhost:3001` (дев), або значення
`NEXT_PUBLIC_API_URL`.

**Формат помилки** (однаковий для всіх ендпоінтів):

```json
{
  "statusCode": 404,
  "message": "Transaction not found",
  "error": "Not Found"
}
```

`message` — рядок для більшості помилок, або масив рядків для помилок
валідації DTO (`class-validator` віддає по одному повідомленню на кожне
недійсне поле).

**Автентифікація.** Усі ендпоінти, крім позначених `@Public()`, вимагають
заголовок:

```
Authorization: Bearer <accessToken>
```

Токен видається `POST /auth/register` або `POST /auth/login`. Немає
або протермінований токен → `401 Unauthorized`.

**Rate limiting.** Базовий ліміт — 100 запитів/хв на кожен маршрут.
`/auth/register` і `/auth/login` додатково обмежені (див. таблицю нижче) —
перевищення повертає `429 Too Many Requests`.

---

## App

### `GET /`

Health check. `@Public()`. Захищений тим самим `@SkipThrottle({ 'auth-ip':
true })`, що й решта контролерів — моніторинг і звичайні пінги не повинні
ділити бюджет, призначений для password spraying на `/auth`.

**Відповідь:** `200 OK`:

```json
{ "status": "ok", "timestamp": "2025-03-01T10:15:00.000Z" }
```

## Auth

### `POST /auth/register`

Реєстрація нового користувача. `@Public()`.

**Rate limit:** 10 запитів/год, за стандартним трекером `@nestjs/throttler`
(ключ — IP; без окремого `getTracker`, на відміну від `/auth/login`).

**Тіло запиту** (`RegisterDto`):

| Поле       | Тип      | Правила                         |
| ---------- | -------- | ------------------------------- |
| `email`    | `string` | має бути валідною email-адресою |
| `name`     | `string` | 2–60 символів                   |
| `password` | `string` | 8–72 символи                    |

```json
{ "email": "user@example.com", "name": "Іван", "password": "supersecret123" }
```

**Успішна відповідь:** `201 Created`

```json
{
  "accessToken": "eyJhbGciOiJI...",
  "user": {
    "id": "uuid",
    "email": "user@example.com",
    "name": "Іван",
    "avatarUrl": null,
    "currency": "UAH",
    "createdAt": "2025-03-01T00:00:00.000Z"
  }
}
```

**Помилки:**

| Код   | Умова                                                                                                                                                                                                                            |
| ----- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `400` | не пройшла валідація DTO                                                                                                                                                                                                         |
| `409` | email вже зареєстровано (перевірка на рівні застосунку; якщо два одночасні запити з однаковим email проходять check-then-act одночасно — той, хто програв гонку, теж отримує `409`, тепер через унікальне обмеження БД, `P2002`) |
| `429` | понад 10 реєстрацій/год                                                                                                                                                                                                          |

---

### `POST /auth/login`

Вхід. `@Public()`. Повертає `200`, не `201` — це не створення ресурсу.

**Rate limit:** 5 запитів/хв, ключ — **IP + email** одночасно (не лише IP:
інакше одна атака на конкретний акаунт з розподілених IP не впреться
в жодну стелю; не лише email: інакше вгадування паролів для випадкових email
з одного IP теж обходить ліміт).

**Тіло запиту** (`LoginDto`):

| Поле       | Тип      | Правила              |
| ---------- | -------- | -------------------- |
| `email`    | `string` | валідна email-адреса |
| `password` | `string` | непорожній рядок     |

**Успішна відповідь:** `200 OK`, та сама форма `AuthResponse`, що й у
`/auth/register`.

**Помилки:**

| Код   | Умова                                                                                                                                                                                                                          |
| ----- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `400` | не пройшла валідація DTO                                                                                                                                                                                                       |
| `401` | невірний пароль **або** email не знайдено — **однакове** повідомлення `"Invalid email or password"` в обох випадках, з випадковою затримкою 50–150 мс перед відповіддю (навмисно: щоб timing-атака не відрізнила два сценарії) |
| `429` | понад 5 спроб/хв для цієї пари IP+email                                                                                                                                                                                        |

---

### `GET /auth/me`

Повертає поточного автентифікованого користувача. Захищений
`JwtAuthGuard`. Викликається фронтендом на кожне монтування захищеної
сторінки для відновлення сесії — тому виведений з-під бюджету `auth-ip`
(`@SkipThrottle({ 'auth-ip': true })`), інакше звичайна навігація вичерпала
б ліміт, призначений для password spraying.

**Відповідь:** `200 OK`, об'єкт `User` (та сама форма, що й `user` у
`AuthResponse`).

**Помилки:** `401` — немає токена, токен протермінований, або токен
посилається на видаленого користувача (`JwtStrategy` перечитує користувача
з БД на кожен запит).

## Categories

Усі маршрути захищені `JwtAuthGuard` і завжди скоуплені на
`@CurrentUser('id')` — користувач ніколи не бачить і не може змінити чужі
категорії.

### `POST /categories`

Створення категорії.

**Тіло запиту** (`CreateCategoryDto`):

| Поле    | Тип      | Правила                                                 |
| ------- | -------- | ------------------------------------------------------- |
| `name`  | `string` | 1–40 символів                                           |
| `color` | `string` | hex-колір, формат `#A3B1FF` (regex `^#[0-9a-fA-F]{6}$`) |
| `icon`  | `string` | 1–40 символів (ім'я іконки `lucide-react`)              |

**Відповідь:** `201 Created`, `CategoryReadModel`:

```json
{
  "id": "uuid",
  "name": "Продукти",
  "color": "#22C55E",
  "icon": "shopping-cart",
  "userId": "uuid"
}
```

**Помилки:** `400` — валідація не пройшла.

---

### `GET /categories`

Список усіх категорій поточного користувача. Без пагінації — очікується,
що категорій у користувача небагато (десятки, не тисячі).

**Відповідь:** `200 OK`, масив `CategoryReadModel[]`.

---

### `PATCH /categories/:id`

Частковий апдейт категорії. Усі поля опціональні — надсилається лише те, що
змінюється (`whitelist: true` в глобальному `ValidationPipe` відкидає
недекларовані поля).

**Тіло запиту** (`UpdateCategoryDto`): ті самі поля, що й `Create`, усі
`?`.

**Відповідь:** `200 OK`, оновлений `CategoryReadModel`.

**Помилки:**

| Код   | Умова                                                                                    |
| ----- | ---------------------------------------------------------------------------------------- |
| `400` | валідація не пройшла                                                                     |
| `404` | `id` не існує **або** належить іншому користувачеві — однакова відповідь в обох випадках |

---

### `DELETE /categories/:id`

Видалення категорії.

**Відповідь:** `204 No Content`.

**Помилки:**

| Код   | Умова                                                                                                                                                                                                                                            |
| ----- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `404` | `id` не існує або належить іншому користувачеві                                                                                                                                                                                                  |
| `409` | категорія має пов'язані транзакції — видалення заблоковано на рівні БД (`onDelete: Restrict` для `Transaction.categoryId`), щоб випадковий `DELETE` не знищив фінансову історію мовчки. `Expense` (застарілу модель), навпаки, каскадно видаляє. |

## Transactions

Усі маршрути захищені `JwtAuthGuard`, скоуплені на `@CurrentUser('id')`.

### `POST /transactions`

Створення транзакції.

**Тіло запиту** (`CreateTransactionDto`):

| Поле          | Тип                           | Правила                                                                                                                                                                          |
| ------------- | ----------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `amount`      | `number`                      | додатне, максимум 2 знаки після коми, ≤ 9 999 999 999.99 (межа стовпця `DECIMAL(12,2)` — без цієї перевірки Postgres кидає numeric overflow і клієнт бачить `500` замість `400`) |
| `type`        | `"INCOME" \| "EXPENSE"`       | —                                                                                                                                                                                |
| `description` | `string \| null`, опціонально | ≤255 символів                                                                                                                                                                    |
| `date`        | `string`                      | ISO 8601                                                                                                                                                                         |
| `categoryId`  | `string`                      | UUID; має належати поточному користувачеві                                                                                                                                       |

**Відповідь:** `201 Created`, `TransactionReadModel`:

```json
{
  "id": "uuid",
  "amount": 42.5,
  "type": "EXPENSE",
  "description": "Кава з клієнтом",
  "date": "2025-03-01T00:00:00.000Z",
  "categoryId": "uuid",
  "userId": "uuid",
  "createdAt": "2025-03-01T10:15:00.000Z"
}
```

**Помилки:**

| Код   | Умова                                                                                                                                                                             |
| ----- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `400` | валідація не пройшла                                                                                                                                                              |
| `404` | `categoryId` не існує або належить іншому користувачеві — той самий `404`, що й для прямого запиту неіснуючої категорії; FK лише доводить, що категорія існує, не хто нею володіє |

---

### `GET /transactions`

Список транзакцій із фільтрами й пагінацією.

**Query-параметри** (`GetTransactionsQueryDto`):

| Параметр     | Тип                     | За замовчуванням | Опис                                                                                                                                                                                                                                     |
| ------------ | ----------------------- | ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `dateFrom`   | ISO дата/дата-час       | —                | включний нижній кордон                                                                                                                                                                                                                   |
| `dateTo`     | ISO дата/дата-час       | —                | верхній кордон; якщо передано лише дату (`2025-03-31`), трактується як "по кінець цього дня" — реально це `< 2025-04-01T00:00:00Z`, оскільки `2025-03-31` парситься саме як `00:00:00Z`; повний timestamp береться як є, без коригування |
| `type`       | `"INCOME" \| "EXPENSE"` | —                | точний фільтр                                                                                                                                                                                                                            |
| `categoryId` | UUID                    | —                | точний фільтр                                                                                                                                                                                                                            |
| `page`       | ціле ≥1                 | `1`              | 1-based                                                                                                                                                                                                                                  |
| `limit`      | ціле 1–100              | `10`             | максимум 100 за раз                                                                                                                                                                                                                      |

**Відповідь:** `200 OK`:

```json
{
  "items": [/* TransactionReadModel[] */],
  "total": 37,
  "page": 1,
  "limit": 10
}
```

`page` повертається таким, яким запитали, навіть якщо він виходить за межі
наявних даних (тоді `items` — порожній масив, а `total` — реальний) —
сервер не намагається "виправити" запит, який промахнувся повз останню
сторінку.

**Помилки:** `400` — невалідні query-параметри.

---

### `GET /transactions/summary`

Місячна статистика: сума доходів/витрат і розбивка за категоріями.

> **Важливо для розробників:** цей маршрут **зареєстрований перед**
> `GET /transactions/:id`. Nest.js реєструє маршрути в порядку оголошення
> методів у класі, і Express матчить перший зареєстрований, що підходить.
> Якби `:id` стояв вище, він би поглинув літерал `summary` як значення `id`,
> і цей ендпоінт повернув би `404`.

**Query-параметри** (`TransactionSummaryQueryDto`, обидва **обов'язкові**):

| Параметр | Тип  | Правила       |
| -------- | ---- | ------------- |
| `month`  | ціле | 1–12, 1-based |
| `year`   | ціле | 1970–9999     |

**Відповідь:** `200 OK`:

```json
{
  "month": 3,
  "year": 2025,
  "income": 15000,
  "expense": 8234.5,
  "balance": 6765.5,
  "byCategory": [
    {
      "categoryId": "uuid",
      "name": "Продукти",
      "color": "#22C55E",
      "icon": "shopping-cart",
      "type": "EXPENSE",
      "total": 3200
    }
  ]
}
```

**Відома межа:** вікно місяця обчислюється в UTC, не в локальному часі
користувача. Транзакція о `2025-03-01T00:30+02:00` (Київ) — це
`2025-02-28T22:30Z`, і вона потрапить у лютневий звіт, а не березневий.
Виправлення потребує зберігати таймзону користувача, чого модель `User`
наразі не робить.

**Помилки:** `400` — `month`/`year` відсутні, не цілі, або поза межами.

### `GET /transactions/:id`

Одна транзакція за id.

**Відповідь:** `200 OK`, `TransactionReadModel`.

**Помилки:** `404` — `id` не існує або належить іншому користувачеві.

---

### `PATCH /transactions/:id`

Частковий апдейт. Усі поля опціональні.

**Тіло запиту** (`UpdateTransactionDto`): ті самі поля, що й `Create`, усі
`?`. **Особливий випадок `description`:** поле не передано → значення не
змінюється; `null` → очищається; рядок → замінюється (three-way handling,
не плутати `undefined` і `null`).

**Порядок перевірок:** спершу перевіряється власність самої транзакції,
і лише потім (якщо `categoryId` присутній у тілі) — власність нової
категорії. Тобто чужий `id` транзакції падає на транзакції, а не на
категорії, навіть якщо `categoryId` теж чужий.

**Відповідь:** `200 OK`, оновлений `TransactionReadModel`.

**Помилки:**

| Код   | Умова                                                                     |
| ----- | ------------------------------------------------------------------------- |
| `400` | валідація не пройшла                                                      |
| `404` | `id` транзакції не існує/чужий, **або** новий `categoryId` не існує/чужий |

---

### `DELETE /transactions/:id`

**Відповідь:** `204 No Content`.

**Помилки:** `404` — `id` не існує або належить іншому користувачеві.
